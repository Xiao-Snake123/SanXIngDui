## 0. 项目一句话定位

**基于 LangGraph 的 Supervisor/Worker 多智能体系统**：把「一句自然语言需求」拆解为
规划 → 史料检索 → 多模态出图 → 异构质检 → 自动回炉（Self-Correction）的闭环，
面向三星堆文物的**场景复原 / 人物还原 / 文物修复 / 风格迁移**四类任务。

技术栈：Python 3.11 / FastAPI / LangGraph / PostgreSQL + pgvector / Redis / SSE 流式；
React 18 + Vite 6 + TypeScript 前端；Qwen2.5-VL + QLoRA 本地微调作为 API 热备。
单测 **14 个文件 / 314 个用例**，另有 A/B 评估基准与 30+ 自检脚本。

## 1. 简历项目经历（可直接粘贴）

> 项目名称：**三星堆文物数字复原 Multi-Agent 系统**　|　角色：独立完成（架构 / 后端 / Agent / 前端联调）

- 设计并实现基于 **LangGraph 的 Supervisor/Worker 多智能体编排**：规划 Agent 产出结构化任务 DAG，Supervisor 负责调度路由，下辖史料检索 / 多模态出图 / 科普文案三个 Worker，末端质检 Agent 构成 **Self-Correction 闭环**；路由函数全部写成纯函数，配合双可用性与步数护栏，杜绝图上死循环。
- 针对「LLM 规划会编造史实」问题，采用 **规则打底 + LLM 增量** 的规划策略：形制要点、材质真相、风格 token 来自人工整理的文物词典构成不可改写的 `locked_form_notes`，LLM 只允许在骨架之上追加视角与验收标准；同时实现 **按角色分层的模型路由**（8 个角色各自声明主模型 + 降级链 + 选型理由 + 成本/延迟预估）。
- 构建 **RAG 证据链路**：BM25（字级 unigram+bigram，含繁→简折叠）与向量检索加权融合，经 Cross-Encoder 重排后进入 prompt；融合系数 α 由 golden set 扫描实测确定（α=0.20 时 R@1 = 0.930 / MRR = 0.956，较原默认 0.45 分别 +0.070 / +0.038）；语料按 `source_type` 派生 `authority` 做可信度加权，向量持久化到 pgvector 并按内容指纹复用。
- 设计 **异构质检机制**：出图侧为 Diffusion，质检侧为「判别式 VLM 五维打分 + 确定性图像统计」加权融合（VLM 0.6 / 客观 0.4，客观塌方时 `min()` 兜底防幻觉放水，时代错配一票否决封顶 0.40）；质检输出可直接转换为 prompt 修改指令，驱动逐轮回炉；配套 `raw_score / capped_by` 字段区分「被封顶」与「分数不够」。
- 排查并修复 **「回炉无效」关键缺陷**：通过构造对照提示词做逐像素比对，实测出图通道存在约 288~436 字的**有效窗口**，原本写在末尾的修正指令从未到达模型；据此把修正指令前置到 prompt 头部并收紧提示词预算到 256 字符，用像素级（而非文件字节）回归脚本守住该结论。
- 工程化与可观测性：实现 **LangGraph / 内置 DAG 双编排引擎**（节点、路由、状态合并语义完全一致，逐项对比单测保障），**逐轮**任务落库（PostgreSQL 7 张表）+ JSONL 轨迹 + Prometheus 风格计数器 + SSE 流式帧协议（含心跳、背压、断连取消），无 API Key / 无数据库 / 无 Redis 时全部降级且**如实上报**，不做静默降级。
- 自评测 A/B 基准（12 条任务集）：相比「单次文生图」基线，多智能体链路风格错配率 0.667 → 0.500（相对下降 25%），代价为单任务延迟 +188ms、平均回炉 0.67 次。**（注：该组数据在无 Key 的全降级通道下测得，样本量 6，面试时须加此限定，见第 7 节）**

## 2. STAR 完整叙述（面试讲述主线）

### S — Situation 业务背景

文物数字复原（三星堆）有四类真实需求：场景复原、人物还原、文物修复、风格迁移。
当时的通行做法是**单次文生图**：用户写一句话 → 调一次扩散模型 → 拿到一张图。这条路在业务上有四个硬伤：

| 业务痛点 | 后果 |
|---|---|
| 文生图是黑盒，无法中途干预 | 用户只有「花钱出图」之后才知道画错没有，改一次重画一次 |
| 模型缺领域知识，会编造史实 | 出现铁器、明清服饰、汉字铭文等**时代错配**，对文博场景是致命错误 |
| 没有质量闸门 | 「是否合格」只能靠人眼判断，无法批量评测与持续迭代 |
| 错误不可追溯 | 出问题不知道是哪个环节：prompt、还是模型、还是标准本身错了 |

### T — Task 目标与约束

目标：构建一个**可干预、可解释、可评估、可追溯**的多智能体系统，输出「有史料依据的复原影像 + 科普文案」。

我给自己定了四条约束（后面每个技术决策都是这四条约束的产物）：

- **可干预**：花钱出图之前，用户能看到 Agent 打算怎么画、依据什么史料、风险在哪，并能逐字改写。
- **可解释**：任何一分扣分都要指向具体位置或现象；任何降级都要如实标注，不许静默返回次品。
- **可评估**：质量必须用可执行、可复现的程序判定，而不是「看起来还行」。
- **可降级地活下去**：无 Key、无数据库、无 Redis、无 langgraph 都能跑完整流程，且不谎报grade。

### A — Action 我做了什么

**① 编排层（`app/graph/`）**：把流程建模为 `planner → supervisor ⇄ {retrieval, restoration, copywriting} → quality → finalize`，`quality → restoration` 构成回炉环。状态用扁平 TypedDict（每个键对应一个生命周期产物）；路由函数是**纯函数**（只读状态返回节点名），不产生副作用、不做 IO，因此全部分支可在无外部依赖的单元测试里穷举。

**② 规划 Agent（`app/agents/planner.py`）**：规则层产出确定性骨架（文物词典里的形制要点、材质真相、风格档案 token、检索 query 基线、验收标准），LLM 层只做增量补全，且被约束为「只能追加、不能删改 `locked_form_notes`」。用户选定提示词时 `prompt_locked=True`，出图侧**首轮逐字下发**、同时关闭平台的 prompt 增强，把「用户的选择被尊重」落成代码契约；而形制要点仍从词典取 —— 提示词可以改，**质检标准不能跟着改**。

**③ Supervisor（`app/agents/supervisor.py`）**：双层决策。规则层给确定顺序与护栏（步数上限、检索上限、禁止在未失效产物上重复劳动）；LLM 只在**真正存在分叉**时介入（质检要求回炉时，判断「补检索」还是「重出图」），输出必须落在白名单内并通过护栏 `_clamp`，否则回退规则层并打点。

**④ 质检 Agent（`app/agents/qa_worker.py` + `app/quality/`）**：异构校验 + 五维加权 VLM + 客观图像统计融合 + 时代错配一票否决 + 双重收敛保护（硬预算 `max_revisions=2` 与收益递减早停 `MIN_GAIN=0.02`）。

**⑤ Self-Correction 闭环（`app/agents/restoration_worker.py`）**：把「规划骨架 + 史料线索 + 参考图残损报告 + 上一轮质检修改指令」四路信息合成新 prompt —— 这是回炉能真的画出不同画面的前提。

**⑥ 检索层（`app/rag/`）**：BM25 + 向量加权融合 + rerank，中文用字级 n-gram 并对古籍做繁→简折叠，融合系数用评测集扫描实测确定。

**⑦ 工程化（其余）**：双编排引擎、逐轮落库 + pgvector 向量复用、SSE 帧协议（心跳 15s / 队列背压 / 断连取消 / contextvars 隔离链路上下文）、统一降级打点、12 条任务的 A/B 评估基准。

## 4. 六个可深挖的技术点（面试弹药，按「讲 15 分钟」准备）

### 4.1 为什么 Planner 不是「让 LLM 直接规划」

**问题**：纯 LLM 规划在这个场景会产生**不可恢复错误** —— 它会把青铜大立人的三层交领写成两层、漏掉赤足方座，而这类型制错误会从 prompt 一路传导到出图与质检；此外无 Key 时整体不可用、同一输入两次规划结果不稳定导致评估无法复现。

**做法**：规则层 `build_rule_plan()` 产出确定性骨架，LLM 层 `refine_with_llm()` 只做增量，且把形制要点 `locked_form_notes` 显式喂回并要求「不得修改」。用户改提示词时标准仍走词典。

**追问接口**：为什么形制要点不能让用户改？→ 因为它同时是质检判定「形制忠实度」的先验；标准跟着提示词变，就等于自己给自己判卷。
**代码**：`app/agents/planner.py:42-50`（硬约束）、`:555-600`（`apply_prompt_override`）。

### 4.2 为什么 Supervisor 要「规则 + LLM 双层 + 护栏」

**问题**：单靠 LLM 调度会跑飞，也会每次经过都烧一次强模型。

**做法**：规则层保证收敛顺序与硬护栏；LLM 只在 `qa.decision == "revise"`（真正存在分叉）时被调用；建议值必须过 `_clamp` 护栏白名单。

**真实事故（最有说服力的一段）**：护栏原先漏了 `give_up` 检查 —— 质检已经判定「收益递减停止回炉」，LLM 仍建议 `restoration`，护栏放行，于是连出 4 轮，2 分钟内打满 DashScope 调用触发 RPM 限流，免费通道也 429，最终交付一张占位图；真正停住它的不是业务判断，而是「已达步数上限强制收敛」。补护栏后才正确走向文案与收敛。
**代码**：`app/agents/supervisor.py:246-288`（注释记录了完整复盘）。

### 4.3 异构质检：为什么不让出图模型自己判自己

**问题**：扩散模型会生成「饱和度完美但给青铜大立人穿上明代官服」的图 —— 客观/语义两类错误只有一半能被单侧尺子抓到。

**做法**：`score = 0.6 × VLM五维加权 + 0.4 × 客观指标`；客观分 <0.5 时用 `min()` 兜底防 VLM 幻觉放水；VLM 报出时代错配则**分数封顶 0.40**（一票否决，不参与加权）。同时输出 `raw_score` 与 `capped_by` —— 实测有一轮融合分 0.745（已越过 0.72 阈值）只因时代错配被压到 0.40，**「被封顶」和「分数不够」是两种完全不同的处境，必须能分开看**，否则用户会去调提示词而不是去修那一处错配。

**还有一个「不质检」的决定**：占位图不做质检。占位图像素只由调色板与前 9 行文字决定，对一张程序画的示意图做「三星堆风格一致性」判定**在物理上没有意义**；早期版本老实跑完 2 轮回炉必然得到 `give_up`，让用户误以为是模型能力不行。现在单独用 `decision="skipped"` 如实标注，且不消耗回炉预算。
**代码**：`app/quality/style_guard.py:189-217`、`app/agents/qa_worker.py:70-152`。

### 4.4 「回炉无效」的根因排查（最有工程味道的一段）

**现象**：回炉了，但两轮画面**逐像素完全相同**，质检分数一模一样 —— 看起来像模型能力不行。

**排查**：构造两个头部相同、只差一句色调描述的提示词分别出图，逐像素比对：

| 提示词长度 | 差异放尾部 | 差异放开头 |
|---|---|---|
| 288 字 | 生效（81.7% 像素不同） | — |
| 436 / 584 字 | **0 个像素不同**（最大像素差 0） | 生效（99.9% 像素不同） |

「挪到开头就生效」同时排除了「上游按整段提示词缓存」的解释 —— 这是**位置**问题，不是缓存问题。

**结论与动作**：① 修正指令前置，且引导语压到 40 字以内（`REVISION n (score x < y) - apply: ...`）；② 免费通道提示词预算取实测窗口以下的保守值 256 字符，截断策略是保留 head 60% + `| ... |` + tail，而不是简单砍尾；③ 回归脚本比对**像素**而非文件字节（早期版本比字节，输出过假 PASS：上游重新编码同一张图，字节不同、像素全同）。
**代码**：`app/agents/restoration_worker.py:265-291`、`app/imagegen/freeimage.py:91-125`、`scripts/check_revision_effect.py`。

### 4.5 RAG：参数不是拍脑袋来的

- 中文**不分词**，用字级 unigram+bigram：领域专名（「青铜纵目面具」）不在通用词典，切词反而切碎召回。
- **繁→简折叠**只作用于检索 token，不改写正文（很多人会问：那用户对油的是原文吗？是的，断言里也不得不 `fold()` 一遍，这正好证明了不篡改原文）。
- 融合系数 α 由 golden set 扫描实测确定，**扫描表原样写在配置注释里**（含「偏 viton 0.60 适合先召回再精排」的权衡说明）。
- 语料 `authority` 不允许手写，由 `source_type` 派生成 property——防止人为拔高可信度；`project_doc / unknown` 类在问答链路强制排除（自己的推测不能当自己的证据）。
- 重排降级用 RRF（k=60）并做归一化 —— 原生 RRF 绝对值太小会让 final score 全部坍缩到 0.011。
**代码**：`app/rag/text.py`、`app/core/config.py:175-196`、`app/rag/store.py:320-364`、`app/rag/corpus.py:171-178`。

### 4.6 工程化：两个「不做作秀」的决定

- **逐轮落库而不是任务结束一次性写**：回炉是逐轮的，第 2 轮跑完时第 1 轮的分必须已可查；而且**钱已经花了**，任务中途崩溃时前面几轮的记录必须留下。`_persist_stopped` 单独把状态写成 `stopped` 且**不写 `decision`**，以免污染通过率的分母。
- **双编排引擎**：真实环境里 `pip install langgraph` 未必成功（私有源缺包 / Python 版本不匹配），所以内置 DAG 调度器与 LangGraph 共享同一批节点函数、路由规则与状态合并语义，行为一致性由专门单测守住 —— **框架是手段，不是目的**。
- **降级如实上报**：连不上数据库不阻断启动，但 `/api/health` 会给出原始异常，而不是静默降级成「看起来一切正常」。统一打点 `sxd_degraded_total{component, fallback}`。
**代码**：`app/graph/runner.py:98,164-178,218-239`、`app/graph/builder.py:115-215`、`app/core/metrics.py:86-119`。

## 6. 面试高频追问 · 答题要点

1. **为什么不用纯 LLM 做规划？** → 会产生不可恢复的形制错误 + 无 Key 不可用 + 不可复现（详见 4.1）。
2. **怎么保证不会死循环？** → 三层：路由纯函数决定有限状态、`recursion_limit = max(25, steps*3)` / 内置引擎硬上限、护栏（已通过 / skipped / give_up / 超预算均禁止回炉）。
3. **怎么防止 VLM 判卷放水？** → 客观指标参与加权 + `<0.5` 时 `min()` 兜底 + 一票否决；并且 Judge 与出图必须**异构**（不同家族 / 不同模态）。
4. **Self-Correction 怎么保证真的改了？** → 四路信息合成 prompt + 指令前置（先吃完 Charlie 窗口）+ 像素级回归脚本。
5. **怎么评估？** → 12 条任务集 A/B 基准（同一 StyleGuard 评分，否则降幅无意义）+ 57 条 golden set 检索评测 + 314 个单测 + SQL 聚合的通过率/回炉次数。
6. **成本怎么控？** → 按角色分层选型（原则：**推理强度随「错误代价」递增，成本随「调用频次」递减**），Supervisor 只在存在分叉时调 LLM；意图解析原本借用 planner 的 qwen3-max，改为 qwen-flash —— 它是受限抽取而非开放创作，且用户在等这一次调用，延迟优先；pgvector 复用向量避免重复计费 embedding；视觉链路可用本地 QLoRA 固定成本替代按图计费。
7. **用户手改了提示词，质检标准会不会跟着漂？** → 不会。`locked_form_notes` 始终从文物词典取，用户输入只影响 `image_spec.prompt`；这是专门的实现约束。
8. **怎么处理幻觉？** → 受限抽取（候选词表由规则预筛后下发，模型只做选择与主体动作句）+ `required_keys` 结构校验 + 白名单夹紧 + 引用必须落在检索结果内否则丢弃并记 caveat。
9. **无外部依赖能不能跑？** → 能。无 Key：规则规划 + 哈希向量 + 免鉴权出图；无 DB：进程内召回（质量不变，只是重启重算向量）；无 langgraph：内置 DAG。全部降级打点上报。
10. **有哪些已知的不足？** → 见第 7 节。主动说比被追问更有分。

## 7. 诚实边界（重要：面试被戳的地方）

**这些数字必须加限定条件，否则容易翻车：**

- **错配率 25% 下降**：`eval_report.json` 生成时 `models_configured: false`、`provider: local-placeholder`，即**全部走了降级通道**，有效样本 **6 条**。可以说「在自建 12 条任务集上，多智能体链路相对单次文生图基线的错配率由 0.667 降至 0.500；但该轮运行在无 API Key 的降级环境下，样本量为 6，结论仍需真实模型通道复测」。**不要**说成「线上效果提升 25%」。
- **语料规模**：README 写「50 条」是 v1 的旧数据；当前加载的是 `data/corpus/v2/` 共 **266 条**（另有 `deprecated/` 56 条刻意不加载）。README 与部分注释已过期，以目录实况为准。
- **测试数量**：README 写「219 个」，实际 **14 个文件 / 314 个 test 函数**（另有 9 处 parametrize）。
- **α 扫描表**：在 v2 语料 **150 条 / 评测集 57 条**的时点测得，语料扩充到 266 条后建议重扫。
- **检索评测集的乐观偏差**：golden set 是通读语料后编写的，测的是「这些主题能否检索到」，而非「任意真实提问能否检索到」—— 代码把这个偏差写在测试文件头了。承认它，反而加分。
- **真实存储链路没有单测覆盖**：为保证测试离线与确定性，`conftest.py` 清掉了 `DATABASE_URL / REDIS_URL`，真实 PG/Redis 链路由 `scripts/check_storage.py` 显式验证。

**项目边界（主动说清，不是减分项）**：这是一个个人主导的端到端项目，没有高并发线上流量验证；Quality Judge 本身仍是 LLM，会存在判定方差；尚未接入真实用户提问日志做闭环迭代。

## 8. 讲述脚本

### 8.1 一分钟版本

> 我做的是一个三星堆文物数字复原的多智能体系统。业务痛点是单次文生图这条黑盒链路：用户花钱出图才知道画错没有，而模型又会编造史实，出现铁器、明清服饰这类致命的时代错配。
> 我的做法是用 LangGraph 搭了 Supervisor/Worker 编排：规划 Agent 负责拆解任务，这里我刻意没有用纯 LLM 规划，而是规则打底、LLM 只做增量，因为形制错误是不可恢复的，会一路传导到出图和质检。中间接了 RAG 提供史料依据，最后的质检 Agent 用「判别式 VLM + 确定性图像统计」做异构校验，时代错配一票否决，不合格就自动回炉 —— 质检输出的不是「重做」而是可直接转成 prompt 的修改指令。
> 最有意思的一次排查是「回炉了但画面逐像素不变」，我做了对照实验测出出图通道存在约 288~436 字的有效提示词窗口，原本写在末尾的修正指令从来没到达模型，改到头部才真正生效。
> 评估上我建了 12 条任务的 A/B 基准，相比单次文生图基线，风格错配率从 0.667 降到 0.500。

### 8.2 三分钟版本（在一分钟基础上展开三处）

1. **为什么 planner 的规则筹码这么重** —— 讲不可恢复错误 + `locked_form_notes` + "提示词可以改，质检标准不能跟着改"。
2. **异构质检的设计** —— 讲融合公式、`min()` 兜底、一票否决，以及 `raw_score/capped_by` 为什么要分开（0.745 被压到 0.40 那次）。
3. **护栏事故复盘** —— 讲 `give_up` 被漏掉导致 2 分钟打满限流那次，说明「Agent 系统的关键是让 LLM 在不该说话的时候不说话」。
