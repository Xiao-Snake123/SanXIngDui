# 专属 RAG 工程化改造方案

> 状态：**设计定稿，待执行**
> 目标：把现在「50 条自撰语料 + 无评估」的检索,改造成**可信出处 + 可量化质量 + 可追溯回答**的领域 RAG。
> 本文是施工依据。执行进度见文末 §9。

---

## 0. 为什么要做这件事:现有 RAG 的真实短板

先说清楚现状,避免把「重写管道」当成目标 —— **管道其实已经不错,烂的是原料和度量**。

### 0.1 现有语料不可用(实测)

```
50 条 / 正文合计 8386 字 / 单条中位 166 字（min 146 / max 213）
```

| 问题 | 证据 |
|---|---|
| **来源是伪来源** | `source` 取值含「本项目内容质量规范」(4 条)、「三星堆主题视觉设计指引」(2 条) —— 这是项目自己的文档,不是史料 |
| **无可追溯字段** | 50 条中 author / publisher / year / page / url **全为空**。而 `corpus.py` 的 docstring 承诺「`doc_id` 可追溯回原始报告页码」—— 现有数据做不到 |
| **可信度是手写的** | 20/50 条 `authority = 1.0`,其中包含上述自我指涉条目。可信度应由「来源等级」派生,不应手写 |
| **文本形态像生成的** | 长度高度集中在 146~213 字、每条整齐 4 个 tags、行文风格统一。这是 LLM 产出后过一遍的形态,不是文献抽取的形态 |

**后果**:检索到的「证据」本身就是模型写的,再接模型回答就是自证循环。这类问题在 demo 里看不出来 —— 回答流畅会被当成成功。

### 0.2 完全没有检索质量度量

`app/eval/harness.py` 评的是**风格错配率**(图像质检),与检索无关。也就是说:

- 无法回答「recall@5 是多少」
- 无法回答「这次改动让检索变好还是变坏」
- 无法回答「换成真实 embedding 值不值得」

**没有评估就没有调参依据。这是 demo 与工程化的分界线。**

### 0.3 现有管道中值得保留的部分

| 要素 | 实现 | 评价 |
|---|---|---|
| 稀疏召回 | 自研 BM25,**字级 unigram + bigram** | 注释写明「为考古专名密集文本设计,不用 jieba」——判断正确。jieba 词典未必有「鱼凫王」「分铸法」,切错反伤召回 |
| 稠密召回 | pgvector HNSW + 余弦,1024 维 | 与 DashScope `text-embedding-v3` 维度一致,无需改 |
| 融合 | 候选集内 max 归一化后**加权求和**(`HYBRID_ALPHA`) | 比 RRF 细粒度,且权重可线上调参 |
| 精排 | DashScope `gte-rerank-v2`,失败回退融合分 | 可选通道,降级正确 |
| 业务加权 | `final = fused × (0.75 + 0.25 × authority)` | 思路对,但 `authority` 的**取值来源**要改(见 §2) |
| 增量 | `content_hash` 覆盖 `searchable_text` | 改标题也会触发重算,细节到位 |
| 可解释 | 每 chunk 带 5 个分数 + `channels` | 排查坏 case 的关键 |

**结论:不推翻管道,补三样硬指标 —— 可信出处、检索评估、语料版本与授权。**

## 1. 目标与职责边界

改造后一条检索管道服务两个消费端:

| 消费端 | 用途 | 约束 |
|---|---|---|
| **A. 复原任务证据供给** | 现有 `retrieval_worker`,产出 `image_cues` / `key_facts` 注入图像 prompt | 维持现有边界:**只找证据,不做创作**(理由见 `retrieval_worker.py` docstring) |
| **B. 领域问答** | 新增,替换 `frontend/.../FloatingAssistant.tsx` 里硬编码且出处无法核实的回答 | 每条事实句必须回带 `doc_id`;检索为空时**明确说无依据**,不得用通用知识补 |

两端共用同一份语料、同一个 `HybridRetriever`、同一套评估集。区别只在下游:一端产出视觉线索,一端产出带引用的答案。

## 2. 数据模型(v2):让「可追溯」真的成立

### 2.1 字段扩展

现状 `source: str` 单字段承载不了可追溯性。新增:

```jsonc
{
  "doc_id": "sxd-report-0012",          // 稳定主键,永不变
  "title": "青铜纵目面具的形制与铸造工艺",
  "text": "……",                          // 证据正文（150~400 字）
  "quote": "……",                         // 原文摘录（受版权约束时只留这一段）

  "citation": {                          // ★ 新增：出处五元组 + 链接 + 抓取日期
    "title": "三星堆祭祀坑",
    "author": "四川省文物考古研究所",
    "publisher": "文物出版社",
    "year": "1999",
    "locator": "上册 第 178 页",          // 页码 / 章节 / 小节
    "url": null,                          // 纸质文献无 URL
    "accessed": null
  },

  "source_type": "excavation_report",    // ★ 新增：决定 authority 与默认权重
  "license": "quote_only",               // ★ 新增：public_domain | cc_by_sa | official_public | quote_only | internal
  "authority": 1.00,                     // ★ 改为由 source_type 派生，不再手写

  "object": "青铜纵目面具",
  "era": "商代晚期",
  "category": "形制",
  "tags": ["纵目", "柱状外凸", "分铸"]
}
```

### 2.2 `source_type` → `authority` 派生规则

**不要再手写 authority。** 按来源等级派生,可复现、可审计:

| `source_type` | authority | 含义 | 可否作为事实依据 |
|---|---|---|---|
| `excavation_report` | **1.00** | 正式发掘报告、考古简报(一手) | ✅ 可以 |
| `museum_official` | **0.95** | 博物馆官方藏品说明、展陈说明 | ✅ 可以 |
| `ancient_text` | **0.90** | 公版古籍原文(《华阳国志》《山海经》) | ✅ 可以(需标注为古代记载) |
| `academic_paper` | **0.85** | 同行评审论文/研究专著 | ✅ 可以 |
| `encyclopedia` | **0.70** | 维基百科等二手汇编(CC BY-SA,须署名) | ⚠️ 仅作线索,尽量回溯源 |
| `news` | **0.50** | 媒体报道、纪录片文案 | ❌ 仅作背景 |
| `project_doc` | **0.30** | **本项目自撰内容** | ❌ **禁止作为史料** |

最后一行是关键:自撰内容必须**显式标记**,而不是伪装成「三星堆博物馆馆藏说明」。检索时默认按类型过滤,问答链路**强制排除** `project_doc`。

## 4. 切分原则

**按「证据单元」切,不按 token 窗口切。** 一物一卡、一议题一卡、一条古籍记载一卡。

| 原则 | 理由 |
|---|---|
| 150~400 字/卡 | 太短缺上下文,太长会让精排与引用定位失效 |
| 每卡独立自洽 | 必须能单独回答「这是什么、出自哪、可不可信」 |
| 不跨主题合并 | 宁可多切,不可混装 —— 混装会让引用无法定位到具体主张 |
| 保留原文引用段 | 有引文才能支撑「可追溯」;没有引文的事实陈述只能算转述 |
| 形制类必带数值 | 「高 262 cm」这类可核验字段要结构化,而不是散在散文里 |

同一文献的多个卡片共享 `citation.locator` 前缀,页码各自独立。

## 5. 索引与召回

保留现有管道,改动集中在这几处:

| 项 | 改动 |
|---|---|
| Embedding | 切到 DashScope `text-embedding-v3`(1024 维,与现配置一致)。**前提:配置 `DASHSCOPE_API_KEY`** —— 当前为空,通道是 `hashing-ngram-1024` 哈希降级 |
| 过滤 | 新增 `source_type` 过滤;问答链路**强制** `exclude: project_doc` |
| 融合权重 | `HYBRID_ALPHA` 用 golden set **网格搜索**决定,不再凭感觉取默认值 |
| query 处理 | 问答场景用户是问句(「大立人手里拿的是什么?」),需先抽取实体与议题再检索。现状直接拿整句当 query |
| 引用回带 | `RetrievedChunk` 增加 `citation` 字段透传到下游 |

**不改**:BM25 字级切分、HNSW 索引、五分数可解释性、`content_hash` 增量逻辑、降级链。

## 6. 评估方案(工程化的分界线)

### 6.1 Golden set

70 条 `{query, 期望 doc_id 集合, 类型, 难度}`,我生成候选 + 你抽检确认。按类型分层,便于定位短板:

| 类型 | 条数 | 例子 |
|---|---|---|
| 专名直查 | 20 | 「青铜纵目面具的纵目有多长」 |
| 语义改写 | 20 | 「大立人手里握的是什么」(史料可能写「环握状」「持物」) |
| 形制数值 | 15 | 「青铜神树有几层几枝」 |
| 跨文档/比较 | 15 | 「三星堆与金沙遗址的关系」 |

### 6.2 指标与阈值

| 指标 | 基线(改造前,现有 50 条) | 目标 |
|---|---|---|
| recall@5 | **待测** | ≥ 0.75 |
| recall@10 | **待测** | ≥ 0.88 |
| MRR@10 | **待测** | ≥ 0.65 |
| nDCG@10 | **待测** | ≥ 0.70 |
| 引用准确率(人工抽检 20 条) | **待测** | ≥ 0.90 |

**先测改造前的基线数字并记录下来。** 没有基线,就无法证明改造有效 —— 尤其无法回答「换真实 embedding 值不值得」。

### 6.3 纳入 CI

评估脚本 `scripts/eval_retrieval.py` 落地为 `tests/test_retrieval_quality.py`,低于阈值直接红。检索质量从此和单测一样有回归保护。

## 7. 问答链路防幻觉契约

| 契约 | 实现 |
|---|---|
| 只能用检索到的片段 | system prompt 明确禁止引入片段外事实(复用 `retrieval_worker.SYSTEM` 的纪律) |
| 每条事实句回带 `doc_id` | 输出 JSON 含 `citations`;无法归属的句子不允许出现 |
| 检索为空则明说 | 答「没有找到依据」,不用通用知识补 —— 这是与普通 chatbot 的核心区别 |
| 争议必须标注 | 学术争议用「存在争议」表述,不得用确定语气(现有 `cautions` 机制) |
| 前端可点开原文 | 引用展示 `citation` + `quote` 片段,让用户能自己核 |

**这一条直接替换掉 `FloatingAssistant.tsx` 里那些无法核实的硬编码引用**(如「《青铜大立人身份考》,《考古》2017年第8期」)。

## 8. 实施步骤与验收

| Phase | 内容 | 验收标准 |
|---|---|---|
| **P1** | 数据模型 v2(schema + 派生 authority + 版本号) | 单测:handwritten authority 会被派生规则覆盖;旧格式能兼容读入 |
| **P2** | 采集脚本 + 首批素材(公版古籍 + 维基,这两类无接口依赖) | ≥ 60 条真实可引用卡片,每条含完整 `citation` |
| **P3** | `sxd.cn` JSON 接口采集 + 国家文物局 | ≥ 200 条;抽样 10 条人工核对与原文一致 |
| **P4** | 配置 Key,切真实 embedding,重算向量 | `/api/corpus` 显示 `dashscope-embedding`,向量复用 0 / 新算 N |
| **P5** | Golden set + 评估脚本 + CI 阈值 | 输出基线 vs 改造后对比;`pytest` 含检索质量断言 |
| **P6** | 问答链路 + 前端引用展示 | 问答回答每条事实可点开原文;检索为空时明说无依据 |

**P5 与 P6 的顺序不可颠倒** —— 没有评估就先做问答,等于没有验收标准。

  | | v1 (旧) | v2 (新) |
  |---|---|---|
  | 条数 | 50 | **151** |
  | 正文合计 | 8,386 字 | **45,373 字** |
  | 可追溯 | **0 %** | **100 %** |
  | 来源类型 | 无 | `ancient_text`(0.90) / `encyclopedia`(0.70) |
  | 授权 | 无 | `public_domain` / `cc_by_sa` |

  **采集期间修掉 4 个「不报错、只是少数据」的坑**(都值得记):

  1. **403 来自 UA,不是网络**。Wikimedia 的 WAF 要求 UA 带可联系标识:
     裸的 `Bot/1.0` 与伪装成 `Mozilla/5.0` 都被 403,只有
     `Name/1.0 (https://…)` 通过。**遇到 403 的直觉反应是伪装 UA,而对方反的就是这个。**
  2. **`prop=extracts` 的 `exlimit` 在全文模式下上限为 1**。一次带 12 个标题只有 1 个返回正文,
     其余在响应里就是一个没有 `extract` 的 page 对象 —— **表现与「页面不存在」几乎一样**。
     若按批量请求实现,会安静地少采 11/12 的页面。
  3. **`redirects=1` 会让 `pages[].title` 变成重定向后的目标**。用它当 key 会让
     「哪些标题没取到」全部错位(实测「三星堆博物馆」→ 繁体「三星堆博物館」被误报为取不到)。
  4. **doc_id 生成不能依赖「抽 ASCII 字符」**。中文标题会退化成空串,
     所有条目共用 `page-NN` 前缀 → doc_id 大面积撞车 → 写出 151 条、装载只剩 129 条,
     **22 条被静默覆盖**,而日志只有一行「语料库就绪: 129 条」。
     改为「标题哈希 + 序号」:既唯一,又**重采得到同一 id**(向量复用才会命中)。

  `check` 子命令里加了**写出行数 vs 装载条数对账**:只报「装载了 N 条」看不见上面第 4 个坑,
  必须与文件真实行数对账才能暴露。

- [x] **P2.5 繁简归一化** ✅ 2026-09-17
  - 现象:`蚕丛 纵目` 查询的 4 条命中**全部是维基简体条目**;

     (`storage/vectors.py` 两个索引实现都嵌 `searchable_text`)。只在分词器里折叠会造成
